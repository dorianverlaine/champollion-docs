---
title: Route A and B
description: The two ways to run riscv64 programs with Champollion — directly on macOS with translated syscalls, or inside an arm64 Linux VM where syscalls are the kernel's.
---

The same translator runs in two settings, and the settings hide different
gaps.

## Route B: on the Mac

`rvrun ./hello` on macOS. The guest lives in one host process; its syscalls are
dispatched to a Darwin backend that translates the differences from Linux, and
everything else behaves like the Linux ABI the program expects. This is the
daily loop: build, run, and debug a riscv64 binary straight from the Mac's own
file system, with no VM in the way.

Debugging lives here too: `rvrun -g 1234 prog` waits for a GDB remote
connection with the guest stopped at its entry point, breakpoints are kept on
the host side (guest code is never patched), and stepping and Ctrl-C are exact.

## Route A: inside a Linux VM

For containers and full distributions, `launcher/` builds `rvcontainer`, which
pulls a `linux/riscv64` image, unpacks it into an ext4 file, boots an arm64
Linux VM, and registers `rvrun` as the VM's `binfmt_misc` handler. Inside the
VM, riscv64 and arm64 share syscall numbers and structure layouts, so guest
addresses are host addresses and any call the runtime does not emulate passes
straight to the kernel. Alpine and Debian roots run `apt`, `bash`, `dpkg`, and
CPython this way, and a guest `execve` is the kernel's again.

Same runtime, different backend: when a syscall is not emulated, route B
translates it to Darwin, and route A hands it to a real Linux kernel.

## Which one runs my program?

Route B is the default on the Mac and covers day-to-day development. Reach for
route A when the program wants a full userland — package managers, service
managers, containers — or when a syscall route B does not emulate is in the
way.
