title: 路线 A 与路线 B
description: 用 Champollion 运行 riscv64 程序的两种方式——直接在 macOS 上跑、由 Darwin 后端翻译系统调用，或者在 arm64 Linux 虚拟机里跑、让内核亲自处理系统调用。
---

同一套翻译器可以跑在两种环境里，而这两种环境掩盖了不同的缺口。

## 路线 B：跑在 Mac 上

在 macOS 上执行 `rvrun ./hello`。客户程序活在单个宿主进程里；系统调用交给 Darwin 后端，由它
翻译与 Linux 的差异；其余部分对程序而言就是它期待的 Linux ABI。这是日常开发的闭环：构建、
运行、调试 riscv64 二进制，全程使用 Mac 自己的文件系统，中间没有虚拟机。

调试也在这里：`rvrun -g 1234 prog` 会等待 GDB 远程连接，客户程序停在入口点；断点保存在宿主
一侧（不会改动客户代码），单步执行和 Ctrl-C 都精确可控。

## 路线 A：跑在 Linux 虚拟机里

面向容器和完整发行版时，`launcher/` 会构建 `rvcontainer`：拉取 `linux/riscv64` 镜像、解包成
ext4 文件、启动一台 arm64 Linux 虚拟机，并把 `rvrun` 注册为该虚拟机的 `binfmt_misc` 处理器。
在虚拟机里，riscv64 与 arm64 共用系统调用号和结构体布局，因此客户地址就是宿主地址，运行时
没有模拟的调用会直接透传给内核。Alpine 和 Debian 的根文件系统就这样运行 `apt`、`bash`、
`dpkg` 和 CPython，而客户自己的 `execve` 也重新交还给内核处理。

同一个运行时，不同的后端：没有被模拟的系统调用，路线 B 把它翻译给 Darwin，路线 A 则把它交到
真正的 Linux 内核手里。

## 该选哪一条？

在 Mac 上默认走路线 B，它覆盖日常开发。当程序需要完整的用户态环境——包管理器、服务管理器、
容器——或者路线 B 尚未模拟的某个系统调用挡在路上时，换路线 A。
